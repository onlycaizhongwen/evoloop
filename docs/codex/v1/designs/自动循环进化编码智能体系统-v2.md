自动循环进化编码智能体系统 - 架构与需求设计文档 (V2)

1. 项目概述

本项目旨在构建一个基于 oh-my-codex (OMX) 运行时、Superpowers 工程化技能与 Codex CLI 底层能力的自动循环编码智能体系统。系统通过上层轻量级编排器（Orchestrator）实现多智能体（Architect、Coder、Reviewer、Fixer）的协作，并引入“组合式门控”与“受控技能进化”机制，实现复杂工程任务的自动化交付。

技术底座可行性依据：
• OMX v0.17.0+：已支持团队编排（$team）、Ralph 循环（$ralph）、Worktree 隔离及插件化技能发现。

• Superpowers：已提供 Codex 技能接入方式，涵盖 TDD、审查、需求澄清等。

• Codex CLI：提供底层代码生成与 Full-auto 执行能力。

3. 需求设计

3.1 功能性需求 (Functional Requirements)

FR-01: 多智能体角色定义与串联

系统需支持以下角色的自动化串联，由 Orchestrator 控制流转：
1.  Architect (架构师): 接收需求，使用 brainstorming 和 writing-plans 技能，输出 plan.json。
2.  Coder (编码员): 接收单项任务，使用 test-driven-development 技能，输出代码与单元测试。
3.  Reviewer (审查员): 接收代码变更，进行静态分析与逻辑检查，输出结构化 JSON 审查报告（含置信度）。
4.  Fixer (修复员): 接收审查失败报告或 CI 报错，进行代码修复。

FR-02: 组合式门控机制 (Hybrid Gating)

为解决“模型自报置信度虚高”问题，系统采用多维评分门控，而非单一依赖模型输出：
1.  硬性指标 (Must Pass)：单元测试覆盖率达标、Lint 检查通过、类型检查（Type Check）通过。
2.  软性指标 (Score Based)：Reviewer Agent 输出 JSON，包含 confidence (0-100) 和 issues 列表。
3.  决策逻辑：仅当硬性指标全通过且软性指标 confidence >= 80 时，任务标记为完成。若置信度不足，Orchestrator 需将 issues 列表反馈给 Fixer Agent 进行迭代。

FR-03: 受控技能进化 (Controlled Evolution)

为防止“错误规则、过度泛化、规则冲突”，技能进化流程必须包含人工审核环节：
1.  检测：Orchestrator 监控日志，识别高频错误（如 >= 3次）。
2.  生成：自动生成候选规则（Draft Rule），存入 pending-rules/ 目录。
3.  审核：不自动生效。需通过 Git PR 或人工确认后，才能合并至正式 Skill 文件（~/.agents/skills/my-project/rules.md）。
4.  加载：仅在下次任务启动时加载更新后的 Skill。

FR-04: 工程化隔离与状态持久化

1.  利用 OMX 的 $team 或 Worktree 机制，确保每个任务或 Agent 在独立的 Git 分支/目录中工作，互不干扰。
2.  所有中间状态（计划、日志、上下文）必须存储于 .omx/ 目录下，支持断点续跑。

3.2 非功能性需求 (Non-Functional Requirements)

ID 需求 说明 应对策略

NFR-01 数据契约完整性 定义 plan.json, review.json, 任务状态的 Schema。 使用 JSON Schema 或 Pydantic Model 校验，防止自动化流程因格式变化崩溃。

NFR-02 安全边界 Full-auto 模式下防止执行危险命令（如 rm -rf）。 1. OMX/OS 层设置命令黑名单。<br>2. 限制工作目录权限。<br>3. 过滤敏感信息（API Key）输出。

NFR-04 可观测性 实时输出各 Agent 状态及门控结果。 解析 OMX 的 HUD 输出或 .omx/ 日志，提供简易 Dashboard。

            Coder_Agent --> 代码生成: 使用 TDD Skill

            硬性检查 --> Reviewer_Agent: 硬性指标通过

            组合门控判断 --> Coder_Agent: 门控失败 (反馈 issues)
        }

    熔断机制 --> 人工介入: 报警并暂停


4.2 关键流程说明

1.  初始化与配置:
    ◦   Orchestrator 检查 Codex CLI、OMX 环境及 API Key。

    ◦   挂载 Superpowers 技能，加载自定义项目规则。

    ◦   安全预设：加载命令黑名单（禁止 rm -rf /, DROP TABLE 等）。

2.  任务微循环详解 (MicroLoop):
    ◦   Step 1 (Code): Orchestrator 发送任务描述给 OMX，指定使用 test-driven-development 技能。OMX 调用 Codex CLI 生成代码。

    ◦   Step 2 (Hard Gate): OMX 自动执行预定义的测试命令（如 pytest）和 Lint（如 eslint）。若失败，OMX 内部循环（Ralph模式）会尝试修复，超过次数则上报 Orchestrator。

    ◦   Step 3 (Soft Gate): 硬性指标通过后，Orchestrator 调用 Reviewer Agent（注入结构化输出 Prompt）。

    ◦   Step 4 (Decision): Orchestrator 解析 Review JSON（需符合预定义 Schema）。

        ▪   Pass: 提交代码 (Git Commit)，更新任务状态。

        ▪   Fail: 提取 issues，构造新的 Prompt，重新进入 Step 1。

3.  受控进化触发:
    ◦   在 Phase 2 结束后，Orchestrator 扫描日志。

    ◦   示例: 如果发现 TypeError: Cannot read property 'x' of undefined 出现多次，生成候选规则："Rule #101: 访问对象属性前，务必进行空值检查"。

    ◦   存入 pending-rules/rule-101.md，等待人工审核合并，而非直接写入 Skill。

5. 落地实施建议 (Roadmap)

1.  Week 1: MVP (最小可行性产品)
    ◦   搭建 OMX + Codex CLI + 国内代理环境。

    ◦   编写简单 Python 脚本作为 Orchestrator，实现：调用 OMX 生成代码 -> 运行测试 -> 打印结果。

    ◦   重点：先实现硬性门控（测试通过），暂不引入复杂的置信度解析。

2.  Week 2: 引入组合门控
    ◦   定义 review.json 的 JSON Schema。

    ◦   在 Orchestrator 中实现 Reviewer Agent 调用与 Schema 校验。

    ◦   设定 80% 置信度阈值，实现自动重试逻辑（最多3次）。

3.  Week 3: 安全与契约
    ◦   增加命令黑名单与安全边界检查。

    ◦   规范化 plan.json 和日志格式，确保数据契约完整。

4.  Week 4: 受控进化
    ◦   实现日志分析模块，尝试生成第一条候选规则。

    ◦   建立人工审核流程（如生成 Git Branch/PR），验证受控进化机制。
