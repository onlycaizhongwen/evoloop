## 3. 需求设计

### 3.1 功能性需求 (Functional Requirements)

#### FR-01: 多智能体角色定义与串联
系统需支持以下角色的自动化串联，由 Orchestrator 控制流转：
1.  Architect (架构师): 接收需求，使用 `brainstorming` 和 `writing-plans` 技能，输出 `plan.json`。
2.  Coder (编码员): 接收单项任务，使用 `test-driven-development` 技能，输出代码与单元测试。
3.  Reviewer (审查员): 接收代码变更，进行静态分析与逻辑检查，输出结构化 JSON 审查报告（含置信度）。
4.  Fixer (修复员): 接收审查失败报告或 CI 报错，进行代码修复。

#### FR-02: 置信度门控机制 (Confidence Gating)
1.  Reviewer Agent 必须输出标准化 JSON，包含 `confidence` (0-100) 和 `pass` (bool) 字段。
2.  Orchestrator 需解析该 JSON。仅当 `confidence >= 80` 且 `pass == true` 时，任务标记为完成并进入下一环节。
3.  若置信度不足，Orchestrator 需将 `issues` 列表反馈给 Fixer/Coder Agent 进行迭代，直至达标或达到最大重试次数（如 5 次）。

#### FR-03: 技能自动进化 (Auto-Evolution)
1.  Orchestrator 需监控 Reviewer 和 Fixer 的执行日志。
2.  当检测到特定类型的错误（如 "NullPointerException"）反复出现（如 >= 3次），Orchestrator 应自动生成一条规则。
3.  将该规则追加至自定义 Skill 文件（如 `~/.agents/skills/my-project/rules.md`）。
4.  后续 Agent 启动时加载更新后的 Skill，避免重复错误。

#### FR-04: 工程化隔离与状态持久化
1.  利用 OMX 的 `$team` 或 Worktree 机制，确保每个任务或 Agent 在独立的 Git 分支/目录中工作，互不干扰。
2.  所有中间状态（计划、日志、上下文）必须存储于 `.omx/` 目录下，支持断点续跑。

### 3.2 非功能性需求 (Non-Functional Requirements)

| ID | 需求 | 说明 |
| :--- | :--- | :--- |
| NFR-01 | 稳定性 | 单个 Agent 崩溃不应影响整体流程，Orchestrator 需具备异常捕获与重启能力。 |
| NFR-02 | 可观测性 | 需实时输出各 Agent 状态（Running/Reviewing/Fixing）及当前置信度。 |
| NFR-03 | 兼容性 | 支持通过 `openai_base_url` 配置国内中转 API，无需依赖原生 OpenAI 网络。 |
| NFR-04 | 可扩展性 | 新增 Agent 角色或 Skill 时，不应大规模修改 Orchestrator 核心调度逻辑。 |

### 4.1 核心执行流图 (Core Workflow)

    state "第二阶段：自动循环执行" as Phase2 {

        state "任务微循环" as MicroLoop {
            Coder_Agent --> 代码生成: 使用 TDD Skill
            代码生成 --> 自动测试: OMX $ralph 执行
            自动测试 --> Reviewer_Agent: 测试通过
            自动测试 --> Coder_Agent: 测试失败 (Fixer逻辑)
            
            Reviewer_Agent --> 置信度判断: 解析 JSON
            置信度判断 --> 任务队列: confidence >= 80% (成功)
            置信度判断 --> Coder_Agent: confidence < 80% (失败/修复)
        }
        
        任务队列 --> 所有任务完成?: 队列为空?
    }

    state "第三阶段：进化" as Phase3 {
        所有任务完成? --> 技能进化检查: 是
        技能进化检查 --> 分析日志: Orchestrator 分析 .omx/logs
        分析日志 --> 更新Skills: 发现重复错误?
        更新Skills --> [*]: 流程结束 / 进入下一Feature
    }

    置信度判断 --> 熔断机制: 重试次数 > 5
    熔断机制 --> 人工介入: 报警并暂停


### 4.2 关键流程说明

1.  初始化与配置:
    ◦   Orchestrator 检查 Codex CLI、OMX 环境及 API Key。

    ◦   挂载 Superpowers 技能，加载自定义项目规则。


2.  任务微循环详解 (MicroLoop):
    ◦   Step 1 (Code): Orchestrator 发送任务描述给 OMX，指定使用 `test-driven-development` 技能。OMX 调用 Codex CLI 生成代码。

    ◦   Step 2 (Test): OMX 自动执行预定义的测试命令（如 `pytest`）。若失败，OMX 内部循环（Ralph模式）会尝试修复，超过次数则上报 Orchestrator。

    ◦   Step 3 (Review): 测试通过后，Orchestrator 调用 Reviewer Agent（注入结构化输出 Prompt）。

    ◦   Step 4 (Gate): Orchestrator 解析 Review JSON。

        ▪   Pass: 提交代码 (Git Commit)，更新任务状态。

        ▪   Fail: 提取 `issues`，构造新的 Prompt（“请根据以下审查意见修复代码...”），重新进入 Step 1。


3.  自动进化触发:
    ◦   在 Phase 2 结束后，Orchestrator 扫描日志。

    ◦   *示例*: 如果发现 `TypeError: Cannot read property 'x' of undefined` 出现多次，自动在 `custom_rules.md` 中添加："Rule #101: 访问对象属性前，务必进行空值检查（Optional Chaining 或 if guard）。"

    ◦   该文件将在下一次 Architect 或 Coder 运行时被加载。

## 5. 落地实施建议 (Roadmap)

1.  Week 1: MVP (最小可行性产品)
    ◦   搭建 OMX + Codex CLI + 国内代理环境。

    ◦   编写简单 Python 脚本作为 Orchestrator，实现：调用 OMX 生成代码 -> 运行测试 -> 打印结果。

2.  Week 2: 引入门控
    ◦   在 Orchestrator 中实现 Reviewer Agent 调用与 JSON 解析。

    ◦   设定 80% 置信度阈值，实现自动重试逻辑（最多3次）。

3.  Week 3: 技能进化
    ◦   实现日志分析模块，尝试自动生成第一条自定义 Rule 并验证其是否被加载。

4.  Week 4: 完善与监控
    ◦   增加 Web UI 或 CLI Dashboard 显示当前进度与置信度曲线。

    ◦   处理边缘情况（网络超时、API 限流）。
