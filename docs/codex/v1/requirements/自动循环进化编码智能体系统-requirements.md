# 自动循环进化编码智能体系统 - 需求文档

## 1. 背景

当前 AI 编码工具已经能够生成代码、执行命令和辅助修复问题，但在真实工程交付中仍存在几个明显缺口：

- Agent 容易只完成“看起来能运行”的局部代码，缺少稳定质量门控。
- 模型自报置信度不可直接作为交付依据。
- 自动执行命令存在误删、越权、泄露敏感信息等安全风险。
- 多轮修复缺少结构化状态，失败后难以恢复和审计。
- 经验沉淀容易停留在聊天记录中，难以转化为可复用规则。

本系统希望在 Codex CLI、oh-my-codex（OMX）和 Skills 机制之上，构建一个自动循环编码智能体系统。系统先以单任务 MVP 闭环为目标，做到可验证、可恢复、可审计，再逐步扩展到多 Agent 协作和受控技能进化。

## 2. 目标

### 2.1 产品目标

- 提供一个可自动执行单个工程任务的编码闭环。
- 在代码生成后自动运行测试、Lint、类型检查和 Review。
- 通过质量门控决定任务完成、重试或暂停。
- 在失败时保留结构化日志、报告和人工介入信息。
- 将重复错误沉淀为候选规则，但不自动污染正式 Skill。

### 2.2 对外表达目标

- 对业务方讲清楚：系统解决什么问题、带来什么价值、风险如何控制。
- 对技术团队讲清楚：系统边界、核心流程、数据契约、实现优先级。
- 对管理方讲清楚：先做 MVP，再做扩展，不追求一开始完全自治。

## 3. 用户与角色

| 角色 | 关注点 | 典型诉求 |
| :--- | :--- | :--- |
| 开发者 | 编码效率、失败定位、可控自动化 | 让 Agent 自动完成小任务，但不要破坏工程 |
| Tech Lead | 质量、架构一致性、团队规范 | 自动化必须可审计、可暂停、可回滚 |
| 测试/QA | 验收标准、回归风险 | 自动修复必须有测试和报告 |
| 运维/安全 | 命令权限、路径边界、敏感信息 | 禁止危险命令和越权修改 |
| 管理者 | 成本、效率、阶段成果 | 有清晰 MVP、路线图和风险治理 |

## 4. 范围

### 4.1 MVP 范围

- 支持读取一个结构化 `task.json`。
- 支持单任务自动编码、检查、审查、修复循环。
- 支持 Hard Check：测试、Lint、类型检查。
- 支持 Reviewer 输出 `review.json`。
- 支持 malformed JSON 最多 2 次重试。
- 支持 `review.task_id == task.task_id` 一致性校验。
- 支持质量评分与通过/重试/暂停决策。
- 支持 Diff 风险评分。
- 支持 `change_type`：`feature`、`bugfix`、`refactor`、`config`。
- 支持安全策略：允许路径、禁止路径、权限等级、危险命令阻断。
- 支持 heartbeat 与运行状态持久化。
- 支持生成 pending rule proposal，但不自动写入正式 Skill。

### 4.2 非目标

- MVP 不做复杂 DAG 自动拆分。
- MVP 不做多任务并行合并。
- MVP 不自动创建 PR、不自动合并主分支。
- MVP 不自动修改正式 Skill。
- MVP 不提供完整 Web Dashboard。
- MVP 不自动处理数据库迁移、生产配置、线上发布等高风险变更。

## 5. 关键场景

### 5.1 Bugfix 自动修复

用户输入一个缺陷任务，系统生成修复代码，运行测试和静态检查，再通过 Reviewer 判断是否有测试缺口或逻辑风险。若质量门控通过，则输出最终报告；若失败，则进入修复循环。

### 5.2 Feature 小需求实现

用户输入一个小功能任务，系统生成代码和测试。若源码变更但未更新测试，Diff 风险评分扣分，Reviewer 需要检查测试缺口。

### 5.3 Refactor 安全重构

用户输入不改变外部行为的重构任务。系统允许源码变化但不强制扣“未新增测试”分，同时要求 Reviewer 确认外部行为未改变。

### 5.4 Config 配置调整

用户输入配置类任务。系统先检查 `forbidden_paths`，未命中时将权限映射为 `elevated`，并记录原因；命中禁止路径则直接阻断。

### 5.5 Reviewer 输出异常

Reviewer 输出非法 JSON 或 `task_id` 不匹配时，系统保存原始输出，并携带字段模板与动态 `task_id` 重新请求 JSON。超过 2 次仍失败，则暂停并输出人工介入报告。

## 6. 功能需求

| ID | 需求 | 优先级 |
| :--- | :--- | :--- |
| FR-01 | 系统应读取并校验 `task.json` | P0 |
| FR-02 | 系统应调用 Coder/Fixer 执行单任务代码修改 | P0 |
| FR-03 | 系统应执行测试、Lint、类型检查等 Hard Check | P0 |
| FR-04 | Hard Check 失败时应短路 Reviewer，直接进入 fix 或 halt | P0 |
| FR-05 | 系统应调用 Reviewer 并解析 `review.json` | P0 |
| FR-06 | Reviewer JSON 非法时应最多重试 2 次 | P0 |
| FR-07 | 系统应校验 `review.task_id == task.task_id` | P0 |
| FR-08 | 系统应计算质量分并做出 done/retry/halt 决策 | P0 |
| FR-09 | 系统应按 Diff 规则计算风险分 | P0 |
| FR-10 | 系统应按 `change_type` 调整测试覆盖扣分策略 | P0 |
| FR-11 | `change_type=config` 时应先检查 forbidden，再映射 elevated | P0 |
| FR-12 | 系统应输出 heartbeat 和阶段日志 | P1 |
| FR-13 | 系统应持久化运行状态和产物 | P1 |
| FR-14 | 系统应生成 pending rule proposal | P2 |

## 7. 非功能需求

| ID | 需求 | 说明 |
| :--- | :--- | :--- |
| NFR-01 | 可恢复 | 任务中断后可根据 `run_state.json` 和产物恢复定位 |
| NFR-02 | 可审计 | 每次尝试、检查、Review、质量判断都应有结构化记录 |
| NFR-03 | 安全性 | 默认限制写入路径、危险命令和敏感文件访问 |
| NFR-04 | 可观测性 | 长耗时命令必须通过 heartbeat 表明进程仍存活 |
| NFR-05 | 可扩展性 | 后续可扩展多 Agent、任务队列和受控技能进化 |
| NFR-06 | 可解释性 | 质量分、失败原因和暂停原因必须可读 |

## 8. 完成标准

MVP 完成时应满足：

- 能完成至少一个 bugfix 类型单任务闭环。
- Hard Check 失败时不会调用 Reviewer。
- Reviewer JSON 异常能重试并保存原始输出。
- `task_id` 不一致能被识别为 malformed review。
- `change_type=refactor` 不会被“源码改但测试未改”误伤。
- `change_type=config` 能触发 elevated 权限映射，且 forbidden 优先。
- 最终能输出 `quality_report.json`、`run_state.json` 和 `final_report.md`。

## 9. 依赖

- Codex CLI 可用。
- OMX 或等价 Agent 调用方式可用。
- 项目具备可执行测试、Lint 或类型检查命令。
- 工作区有可写目录和可配置安全策略。
- Skills 机制可加载项目规则。

## 10. 风险

| 风险 | 应对 |
| :--- | :--- |
| 模型输出不稳定 | Schema 校验、JSON 重试、task_id 强校验 |
| 自动命令危险 | 权限等级、命令策略、路径策略 |
| 质量门控误判 | Hard Check + Review + Diff 风险组合评分 |
| 任务无限循环 | 最大尝试次数和熔断规则 |
| 技能进化污染 | 只生成候选规则，人工审核后生效 |
